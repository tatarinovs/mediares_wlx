# Прогрев WDX: проверка на аудио и фото

16 ноября 2026, Windows, Ryzen 7 5700X (8 ядер / 16 потоков).

Текущий режим: прогрев только хэшей, отпечатков и резкости. Метаданные и
длительность читаются и кэшируются по запросу TC. Замеры ниже выполнены
на первоначальном варианте с прогревом всех запрошенных групп данных.

Соседи теперь фильтруются также по расширению без учёта регистра.
Для каждого расширения создаётся отдельная очередь. Проверка смешанной папки
BMP/PNG подтверждает исключение чужого формата, совместимость .bmp/.BMP
и работу обеих очередей после запросов обоих форматов.
Лимит 32 относится к просмотренным записям каталога, включая пропущенные.

Прогрев работает через существующие запросы WDX: интерфейс поиска и выдача
результатов остаются в Total Commander. По умолчанию используются три фоновых
работника. Запросы TC пополняют запас до 32 записей каталога на запрошенную
группу данных. Подпапки самостоятельно не обходятся. Константы и определение
типа медиа не запускают прогрев. Метаданные не запускают хэширование.

## Методика

Тест `scripts/test_prefetch.py` вызывает настоящую DLL через ContentGetValueW
последовательно, как потребитель WDX-полей. Каждый проход — новый процесс
и новая отдельная SQLite-база под `target/`; пользовательский кэш не менялся.
Медиа читались на месте, без копирования и изменения оригиналов.

После предварительного прохода выполнены три повторения с 0, 3 и 7 фоновыми
работниками. Порядок во втором повторении обратный. Файловый кэш Windows
не сбрасывался. Фоновые сборки других проектов не останавливались, поэтому
время проходов колебалось. Значения всех полей сравнивались между режимами и совпали.
В таблице медианы времени получения всех значений; завершение работников
измерялось отдельно. Это замеры API, а не времени работы интерфейса TC,

## Проверки и ограничения

- Общая работа одного файла/версии в одной группе кэша не дублируется:
  прямой запрос ожидает уже запущенный расчёт. При отмене фонового расчёта
  прямой запрос может выполнить его заново.
- Отмена TC и новый запрос из другой папки снимают старый прогрев.
  Выгрузка WDX отменяет задания и присоединяет работников перед очисткой кэша.
- Проверены ограничение прогрева, повторный запуск после выгрузки, отсутствие
  записей хешей при запросах размеров фото и аудиометаданных, совпадение результатов.
- В коротких фоновых SQLite-операциях соединение сериализуется, чтобы
  одновременные записи не терялись из-за занятого внутреннего mutex.
  Быстрые UI-запросы по-прежнему не ждут соединения; внешняя блокировка
  SQLite по-прежнему считается промахом кэша.
- Приведённые выше замеры сделаны до разделения анализа аудио: отпечаток, PCM-хеш
  и длительность тогда вычислялись вместе. Теперь расчёт, кэширование и прогрев
  двух хешей независимы; запрос длительности не запускает хеширование.
  Форматы значений полей сохранены, новые записи используют отдельные слоты кэша.
- Плагин не знает маску и сортировку поиска TC. Прогрев может прочитать
  исключённые фильтром соседние файлы; запас ограничен. При другом порядке
  запросов ускорение может быть меньше. Первую порцию читает с начала каталога.

Настройка перенесена в `mediares.ini`, секция `[Settings]`:
`PrefetchThreads=0` отключает прогрев, по умолчанию используется `3`.
Для более интенсивной обработки можно задать `PrefetchThreads=7`;
максимум — 8 фоновых работников, дополнительно ограниченных числом CPU.
После изменения перезапустите TC. GUI сохраняет ручной ключ при записи настроек.
Исходные замеры выше сделаны до переноса настройки из переменной окружения;
приведённые контрольные суммы относятся к той сборке.

После переноса настройки проверены оба варианта DLL: отключение через INI
в папке настроек TC и приоритет INI рядом с DLL. Отдельный тест сохранения
настроек просмотрщика подтверждает сохранность ручного ключа. Новые артефакты:
`target/prefetch-tests/2297c309` (WDX), `target/prefetch-tests/25515797`
(совмещённая DLL), `target/cache-check-282a3e86d45c4b33b9fc3d26ae34ad27`
(повторные процессы, метаданные, блокировки, повреждение базы и WLX).
Пересобранные релизные DLL имеют SHA-256:

- WDX: `ba47df56109cac6c837b8af07620176e910a765d2531af779cd48e405d0e1ab7`.
- WLX: `10d35f1930c821a1ad86d8ff48b8a53fe32d844d76a6b93bbe52279d88a2f013`.

Воспроизведение:

```powershell
python scripts/test_prefetch.py --dll dist/mediares_wdx_only.wdx64
python scripts/test_prefetch.py --dll dist/mediares_wdx_only.wdx64 --benchmark D:/MP3 D:/фотки
```

## Разделение отпечатка и PCM-хеша

Расчёт, RAM-кэш, SQLite-записи и очереди прогрева двух аудиохешей теперь
независимы. PCM-хеш не запускает FFT, отпечаток не хеширует PCM-сэмплы.
Длительность использует готовый результат любого хеша либо отдельно считает
декодированные кадры без хеширования. При запросе обоих хешей нужны два прохода.
Готовые результаты прежнего общего кэша читаются без пересчёта; схема и VERSION=1
сохранены, новые записи используют слоты 10/11/12.

На 24 MP3 из `D:\MP3\Off spring` значения всех трёх полей совпали с предыдущей
релизной DLL. Проверена также загрузка новой DLL с копией прежней базы:
результаты совпали, строки SQLite не изменились. Результаты сравнения сохранены
в `target/audio-split-validation/{old,new,reuse}.json`. Это проверка совместимости,
а не новый замер скорости: параллельно выполнялась сборка.

Расширенный `test_prefetch.py` проверяет независимость полей в RAM и SQLite,
отдельный прогрев хешей, обе очереди одновременно и тихие файлы.
Проверка окончательных архивов: `target/prefetch-tests/3615eeab` (WDX),
`target/prefetch-tests/4fd95c0d` (совмещённый WLX/WDX).
Полный набор проверок дискового кэша и WLX:
`target/cache-check-ed9cd350ab9b4b0a94f7b49d90f8b062`.

После разделения пройдены workspace-тесты MSVC/MinGW, clippy с `-D warnings`,
сборка core без audio-decode, проверка формата и упаковки. Тест общего флага
отмены вынесен в отдельный тестовый executable, чтобы параллельные запросы полей
в соседних тестах не сбрасывали проверяемый флаг.
SHA-256 окончательных DLL:

- WLX: `397ae3917946827725a7ccf4bf9338dc52019e0333b93ecce82a71df8e71662e`.

## Ограничение прогрева тяжёлыми расчётами

Прогрев оставлен только для хэшей изображений, видео- и аудиоотпечатков,
PCM-хеша и резкости. Метаданные и декодированная длительность не создают
фоновых потоков и не открывают соседние файлы; RAM/SQLite-кэш по запросу сохранён.
Настройка PrefetchThreads и предел 32 записи каталога действуют для тяжёлых групп.

На обеих окончательных DLL проверено, что один запрос размеров/формата пикселей,
EXIF, аудиотегов, видеометаданных, видеотегов или длительности кэширует ровно один
запрошенный файл даже после ожидания. Для хэшей и резкости проверен реальный
прогрев соседей, для двух аудиохешей — независимость очередей и результатов.
Артефакты: `target/prefetch-tests/067d4b61` (WDX),
