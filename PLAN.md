# Mediares — Total Commander WDX + Combo (WDX+WLX) плагин

План разработки: развитие существующего плагина `media_dup_finder_wdx` (Total Commander WDX, Rust) в проект **Mediares** — с отдельной облегчённой WDX-сборкой (поиск дубликатов, для тех, кто пользуется сторонним вьювером вроде Imagine) и полной 2-в-1 сборкой (WDX+WLX в одном файле, с просмотром по F3).

Базовый репозиторий: https://github.com/tatarinovs/media_dup_finder_wdx

---

## 1. Цель проекта

Один Rust-репозиторий (workspace), из которого собираются **два независимых релизных артефакта**, без дублирования кода и без поддержки двух репо:

- **`wdx`** — облегчённый Content-плагин: вычисление перцептивных хешей и метаданных фото/видео для поиска дубликатов в TC. Для тех, кто уже пользуется сторонним вьювером (например, Imagine) и хочет только дедуп-поиск.
- **`combo`** — тот же WDX-функционал **плюс** WLX-просмотр по клавише **F3**: фото, видео (с транспортным контролом, fullscreen+overlay), аудио (обложка + транспортный контрол, опционально waveform, опционально плейлист). Это основной кейс — 2-в-1 плагин в одном физическом файле.

Декодирование намеренно разделено по пайплайнам (общие для обеих сборок через `core`):
- **Фото** — общий декодер на базе крейта **`image`** (pure Rust), дополненный отдельными pure-Rust декодерами для форматов, которые `image` не покрывает "из коробки" (AVIF, JPEG XL, SVG).
- **Видео** — **Windows Media Foundation** (WinAPI/COM), как уже сделано в WDX — своего/pure-Rust видеодекодера не пишем.
- **Аудио** — pure Rust пайплайн (`symphonia` для декодинга + `cpal`/`rodio` для вывода звука), без зависимости от MF для чистых аудиофайлов. Актуально только для `combo` — `wdx`-сборке аудио-плеер не нужен.

## 2. Нецели (что сознательно не делаем в первой версии)

- Редактирование/конвертация медиафайлов (отдельная пакетная конвертация форматов сознательно не встраивается в этот плагин — для этого уже есть отдельная CLI-утилита [bpdf](https://github.com/tatarinovs/bpdf)).
- Полный RAW-декодинг (демозаик, цветокоррекция) — берём только встроенный в RAW-файл JPEG/preview (см. раздел 4.2.1), честного RAW-рендеринга не делаем.
- HEIC/HEIF — не пишем/не подключаем декодер: там обычно нет "бесплатного" embedded-JPEG (Apple хранит превью тоже в HEVC), а зрелого pure-Rust HEVC-декодера нет. Оставляем вне поддержки в первой версии.
- Субтитры для видео.
- Кросс-платформенность — проект остаётся Windows-only (видео идёт через WinAPI/Media Foundation).
- Отдельный WLX-only релиз (WLX без WDX) — не нужен, `combo` уже покрывает и WDX, и WLX сразу.

### 3.2 Как это ложится на файловую систему Total Commander

`core` — не `cdylib`, а обычная библиотека: Cargo **статически линкует** её код внутрь `wdx` и `combo` на этапе компиляции. В рантайме отдельного `core.dll`/`core.so` не существует — весь код уже "впаян" в каждый cdylib. Поэтому раскладка в установленном TC простая, без всякой третьей папки под ядро:

```
Commander_path/
└── Plugins/
    ├── wdx/
    │   └── mediares/
    │       └── mediares.wdx64        ← ядро уже статически внутри (лёгкая версия: только decode+hashing)
    └── wlx/
        └── mediares/
            └── mediares.wlx64        ← БАЙТ-В-БАЙТ ТОТ ЖЕ ФАЙЛ, что и combo-cdylib, просто под другим именем
```

Для combo-релиза `mediares.wdx64` и `mediares.wlx64` — **один и тот же собранный `combo`-бинарник**, скопированный инсталлятором под двумя именами в две стандартные папки. TC определяет тип плагина по тому, в какой раздел `wincmd.ini` (`[ContentPlugins]` / `[ListerPluginsWin64]`) и под каким именем он зарегистрирован — не по содержимому файла, так что один физический DLL спокойно отвечает на оба протокола сразу (в нём просто есть все нужные для обоих API экспортируемые функции).

### 3.3 Как избежать дублирования между `wdx/` и `wdx_fields.rs` в `combo/`

И `wdx`, и `combo` реализуют один и тот же набор WDX-функций (`ContentGetValue` и т.д.). Чтобы не писать эту обвязку дважды:
- Сама логика вычисления значений полей (`Image_dHash`, `Video_Fingerprint` и т.д.) уже целиком живёт в `core` (в `hashing.rs`/`image_decode.rs`/`video_frame.rs`) — то есть THE logic не дублируется по определению.
- Тонкую FFI-обвязку (`ContentGetValue`, разбор `field_index`, форматирование под тип TC ожидает) стоит вынести в **саму `core`** как публичную функцию вида `core::wdx_api::content_get_value(...)`, а `wdx/src/lib.rs` и `combo/src/lib.rs` — оба просто дают ей `extern "system"`-обёртку в одну строчку. Тогда дублирования нет вообще ни на одном уровне — есть только два тонких `#[no_mangle] extern "system" fn ContentGetValue(...) { core::wdx_api::content_get_value(...) }` в разных крейтах.

### Ключевые архитектурные решения

1. **Два физических файла, не один DLL под двумя именами при wdx-only.** `wdx`-релиз — самостоятельный, урезанный `mediares.wdx64` (без Win32-окон, без `cpal`/`symphonia`/`resvg` — все эти зависимости даже не компилируются в него благодаря feature-флагам `core`). `combo`-релиз — один файл, скопированный под двумя именами (`wdx64`+`wlx64`) — см. 3.2.
2. **`core` не должен ничего знать про Win32-окна.** Он занимается только декодированием/хешированием/метаданными/тонкой WDX-FFI-обвязкой (3.3). Весь UI-код и WndProc — только в `combo/`.
3. **Видео и аудио — разные пайплайны, не единая обвязка.** Для видео (контейнер с видео+аудиодорожкой) остаёмся на `IMFMediaEngine` — переизобретать av-sync вручную нет смысла. Для чистых аудиофайлов используем полностью pure-Rust пайплайн `symphonia` (декодинг PCM) → `cpal`/`rodio` (вывод на звуковую карту), без зависимости от того, какие аудиокодеки установлены в системе через MF.
4. **Фото — тоже полностью pure-Rust.** Базовые форматы — через крейт `image`, форматы вне его покрытия (AVIF, JPEG XL, SVG) — через отдельные pure-Rust декодеры в `image_decode_ext.rs`. WIC не используется вовсе.
5. **RAW и PSD — не декодируем, а "распаковываем".** Файл уже содержит готовое растровое превью (embedded JPEG у RAW, composite/merged image у PSD) — достаточно найти и выдать его. Извлечённое превью прогоняется через тот же `hashing.rs`, что даёт бесплатную возможность WDX находить дубликаты вида "RAW + его JPG-экспорт" — работает в обеих сборках (`wdx` и `combo`), поскольку это часть `core`.
6. **Состояние на инстанс.** TC может открыть несколько окон Lister одновременно (F3 на разных файлах) — состояние должно храниться per-`HWND` (например, `HashMap<HWND, InstanceState>` за мьютексом, либо `GWLP_USERDATA` с указателем на `Box<InstanceState>`), а не в глобальных статических переменных. Актуально только для `combo`.
7. **Fullscreen — отдельное top-level окно, не расширение embedded child-окна.** `fullscreen.rs` создаёт `WS_POPUP`+`WS_EX_TOPMOST` окно на весь монитор (через `MonitorFromWindow`/`GetMonitorInfo`, с учётом мультимониторности), рендерит тот же контент, что и embedded-режим. `overlay.rs` — общий для fullscreen и embedded UI-слой: полупрозрачные панели поверх контента, показываются на `WM_MOUSEMOVE`/скрываются по таймеру бездействия (`SetTimer` + `TrackMouseEvent` с `TME_LEAVE`), не должны прятаться, пока пользователь взаимодействует с контролом (drag таймлайна).
8. **Плейлист — надстройка над `ListLoadNext`, не отдельный движок.** `playlist.rs` использует то же перечисление файлов папки, что TC даёт через `ListLoadNext`, добавляя свою логику автоперехода/shuffle/repeat поверх уже существующего механизма переключения.

## 4. Функциональные требования

### 4.1 WLX (только `combo`) — общие для всех типов
- [ ] `ListLoad(ParentWin, FileToLoad, ShowFlags)` — определяет тип файла (фото/видео/аудио) через `core::probe`, создаёт дочернее окно нужного вида, возвращает `HWND`.
- [ ] `ListLoadNext` — переключение на следующий/предыдущий файл в папке без пересоздания окна (или с пересозданием — на выбор, но плавнее без).
- [ ] `ListCloseWindow` — корректная остановка `IMFMediaEngine`, освобождение COM-объектов.
- [ ] `ListGetDetectString` — единая строка со всеми поддерживаемыми расширениями (фото+видео+аудио).
- [ ] `ListSearchText` — можно не реализовывать полноценно (не текстовый просмотрщик), либо no-op.
- [ ] `ListNotificationReceived` — обработка `lc_newparams` (смена размеров/шрифта TC), паузы при потере фокуса окна.
- [ ] `ListSendCommand` — минимум `lc_copy` (Ctrl+C — копировать кадр/файл), опционально.
- [ ] `ListGetPreviewBitmap` — (опционально, для thumbnails-режима TC) — превью как миниатюра.

### 4.2 Просмотр фото (только `combo`)
- [ ] Декодирование через `image` crate (и доп. декодеры из 4.2.1/4.2.2) в буфер, совместимый с рендером (RGBA/BGRA).
- [ ] Масштабирование под окно с сохранением пропорций (letterbox).
- [ ] Zoom колёсиком мыши, pan через drag.
- [ ] Поддержка анимированных GIF/WEBP (таймер покадрового воспроизведения).
- [ ] **Базовые форматы (через `image`, уже используется в WDX):** JPG, JPEG, PNG, GIF, WEBP, BMP, TIFF, TIF, ICO — плюс "бесплатные" через тот же крейт: TGA, PNM/PBM/PPM, DDS, HDR, farbfeld.
- [ ] **Новые форматы через отдельные pure-Rust декодеры:**
  - AVIF — `rav1d` (pure-Rust порт dav1d) + `avif-parse`
  - JPEG XL (JXL) — `jxl-oxide`
  - SVG — рендер в растр через `resvg`/`usvg`/`tiny-skia`
  - QOI (Quite OK Image) — крейт `qoi`

#### 4.2.1 RAW-форматы (через embedded-preview, без честного RAW-декодинга) — в `core`, доступно и `wdx`, и `combo`
- [ ] Поддержка CR2, CR3, NEF, ARW, ORF, RW2, DNG, RAF, PEF (список уточнить/сузить под реальные нужды).
- [ ] `core::raw_preview`: структурный обход TIFF/IFD (включая SubIFD, тег `0x14A`) — поиск тегов `JPEGInterchangeFormat`/`JPEGInterchangeFormatLength` (`0x201`/`0x202`), выбор **самого большого** найденного JPEG-блока.
- [ ] Fallback: сигнатурный поиск `FF D8 FF ... FF D9` через `memchr`, если структурный парсинг не смог распознать вариант формата — тоже выбираем самый большой найденный блок.
- [ ] В `image_view.rs` (`combo`) — пометка в UI ("Preview"), что показан встроенный JPEG-превью, а не честный RAW-рендер.
- [ ] Извлечённый JPEG прогоняется через `hashing.rs` в обеих сборках — бесплатная находка дублей "RAW + JPG-экспорт" уже в `wdx`.

#### 4.2.2 PSD (Photoshop) — тот же приём, что и для RAW, в `core`
- [ ] `core::psd_preview`: извлечение composite/merged image data или превью-ресурса (`0x0410`) без парсинга слоёв.
- [ ] Fallback на сигнатурный поиск, если структура нестандартная.

### 4.3 Просмотр видео (только `combo`, WinAPI/Media Foundation — как в WDX, без pure-Rust декодера)
- [ ] Воспроизведение через `IMFMediaEngine` (`playback_video.rs`), рендер в дочерний `HWND` — видео и его аудиодорожка идут одним потоком, av-sync берёт на себя MF.
- [ ] Transport bar: play/pause, таймлайн с перемоткой (drag + click-to-seek), текущее время / общая длительность, громкость/mute.
- [ ] Автопауза при `ListCloseWindow` / потере видимости.
- [ ] Список форматов — как в WDX: MP4, MKV, AVI, MOV, WMV, WEBM, M4V, FLV, TS, MTS.

### 4.4 Просмотр аудио (только `combo`, полностью pure-Rust пайплайн, без MF)
- [ ] Декодинг в PCM через `symphonia` (`core::audio_decode`) — MP3, FLAC, WAV, M4A/ALAC, OGG (Vorbis/Opus), MKA, CAF.
- [ ] Вывод звука через `cpal` или `rodio` (`playback_audio.rs`) поверх WASAPI — без обращения к `IMFMediaEngine`.
- [ ] WMA/AAC (вне контейнера MP4) — проверить покрытие `symphonia`; если не поддерживается — оставить через MF как узкий fallback именно для этих двух форматов (см. риски).
- [ ] Обложка альбома — из тегов (`lofty`, pure Rust), fallback — иконка-заглушка.
- [ ] Строка "Артист — Трек" из тегов (`lofty`), fallback — имя файла.
- [ ] Тот же `transport_bar.rs`, что у видео (переиспользуется, но управляет `playback_audio`, а не `playback_video`).
- [ ] (Фаза 5, опционально) Waveform-визуализация вместо/вместе с обложкой — агрегация PCM из `core::audio_decode`.

### 4.5 Полноэкранный просмотр с overlay-контролами (только `combo`, фото и видео)
- [ ] `fullscreen.rs`: переключение embedded ⇄ fullscreen (по кнопке в overlay, двойному клику по контенту, `Esc`/`F11` для выхода из fullscreen).
- [ ] Fullscreen-окно — `WS_POPUP`+`WS_EX_TOPMOST` на весь монитор, определение монитора через `MonitorFromWindow`/`GetMonitorInfo` (корректно при нескольких мониторах).
- [ ] Layout overlay: заголовок/имя файла — верхний левый угол; свернуть (выход из fullscreen) + закрыть — верхний правый угол; transport bar (для видео: play/pause, таймлайн, время, громкость; для фото: prev/next) — снизу.
- [ ] Все overlay-контролы рисуются поверх контента (полупрозрачные панели), не сдвигая сам кадр/фото.

## 5. Нефункциональные требования

- **Производительность:** переключение между файлами в папке (`ListLoadNext`) — не более 200–300 мс до появления первого кадра/обложки для файлов среднего размера.
- **Память:** корректное освобождение COM-объектов и декодированных буферов при `ListCloseWindow` — проверять через инструменты вроде `!heap` / утечки COM-ref-count в debug-сборке.
- **Совместимость:** Windows 10/11 x64, Windows 7 SP1 x64 (тот же уровень, что заявлен для WDX) — актуально для видео (зависит от системных MF-кодеков, как и сейчас в WDX). Фото и аудио декодируются pure-Rust стеком (`image`+доп. декодеры, `symphonia`) и не зависят от того, какие кодеки установлены в системе.
- **Стабильность:** плагин не должен приводить к падению Total Commander — все `panic!` в Rust-коде должны перехватываться на границе FFI (`catch_unwind`) перед возвратом в TC. Актуально для обеих сборок.
- **Размер:** `wdx`-сборка не должна тянуть зависимости `combo` (Win32-окна, `cpal`, `symphonia`, `resvg`, `rav1d` decode для AVIF можно оставить и в wdx, т.к. полезно для хеширования AVIF-дублей — но всё, что чисто UI/playback, строго исключается через feature-флаги `core`).
- **Установка:** два независимых архива, каждый ставится через свой `pluginst.inf` (`pluginst-wdx.inf` / `pluginst-combo.inf`); combo-инсталлятор кладёт один и тот же файл в обе стандартные папки плагинов под нужными именами.

## 6. Риски и открытые вопросы

| Риск / вопрос | Комментарий | Нужно решить в фазе |
|---|---|---|
| `pluginst.inf` — поддерживает ли один архив установку в обе секции ([ContentPlugins]+[ListerPluginsWin64]) одним файлом под двумя именами | Нужно проверить синтаксис `pluginst.inf` на предмет нескольких `[PluginInstall]`-секций с разным `type=`, указывающих на один и тот же файл; если не поддерживается — делать два шага установки или два `copy`-действия в одном инсталляторе | Фаза 6 |
| Feature-флаги `core` могут случайно потянуть лишнее в `wdx` при неаккуратном `Cargo.toml` (`default-features` по умолчанию) | Явно `default-features = false` в `wdx/Cargo.toml`, включать только нужные фичи вручную; проверять размер `wdx64` в CI как регрессионный тест | Фаза 0 |
| Overlay может мигать/дёргаться при частом `WM_MOUSEMOVE` без дебаунса | Сбрасывать таймер, а не пересоздавать overlay каждый раз; перерисовывать только при реальном изменении видимости | Фаза 3.5 |
| Полноэкранное `WS_POPUP`-окно может конфликтовать с полноэкранным режимом самого TC/Lister | Проверить поведение при уже открытом Lister в собственном floating-режиме TC | Фаза 3.5 |
| Плейлист поверх `ListLoadNext`: TC сам может дёргать `ListLoadNext` при навигации стрелками — нужно не конфликтовать с собственным автопереходом плагина | Явно разделить "пользователь нажал стрелку в TC" и "плагин сам переключил по окончании воспроизведения" | Фаза 5 |
| WMA/AAC (standalone, не в MP4) могут быть не покрыты `symphonia` | Проверить фактическое покрытие; если нет — узкий fallback именно на эти 2 формата через `IMFMediaEngine`, не переписывать весь аудио-пайплайн | Фаза 4 |
| `rav1d` (AVIF) — время сборки и размер зависимостей | AV1-декодер тяжелее прочих pure-Rust декодеров по времени компиляции; проверить приемлемость на CI/локальной сборке, в т.ч. для `wdx`-таргета | Фаза 2 |
| `jxl-oxide` / `resvg` — зрелость и скорость декодинга на больших файлах | Оба активно развиваются, но стоит замерить время декодинга на реальных файлах перед тем как класть в MVP | Фаза 2 |
| RAW-файл без embedded-JPEG подходящего размера (редкие камеры/настройки) | Нужен явный fallback: показывать маленький thumbnail (если есть) или заглушку "превью недоступно", не пытаться честно декодировать | Фаза 2 |
| Чтение тегов через MF `IMFMetadataProvider` ненадёжно для части форматов | Не используем MF для тегов вовсе — только `lofty` | Фаза 4 |
| DPI-scaling панели TC при ресайзе Lister-окна | Обрабатывать `WM_DPICHANGED`/пересчитывать при `WM_SIZE` | Фаза 2–3 |
| Поведение TC "quick view panel" (маленькое окно) vs полноэкранный F3 | Layout transport bar должен адаптироваться к минимальным размерам | Фаза 3 |
| Общий `HWND`-стейт при нескольких открытых Lister-окнах одновременно | Хранить состояние per-instance, не в глобальных статиках | Фаза 2 |
| Паника Rust-кода не должна ронять TC | `catch_unwind` на границе каждой экспортируемой функции, в обеих сборках | Фаза 1 |
| Лицензии новых зависимостей (`lofty`, `symphonia`, `cpal`/`rodio`, `rav1d`, `avif-parse`, `jxl-oxide`, `resvg`/`usvg`/`tiny-skia`, `qoi`, `memchr`) | Проверить совместимость лицензий (в основном MIT/Apache-2.0/BSD, но `rav1d` стоит проверить отдельно) с текущей лицензией проекта | Фаза 0 |

## 8. Критерии готовности (Definition of Done)

- Из одного репозитория, одной командой CI, собираются оба релизных архива — `wdx`-only и `combo` — без дублирования исходников.
- `wdx`-архив ставится и работает независимо, без каких-либо WLX/UI-зависимостей в бинарнике.
- `combo`-архив ставится одним архивом, один и тот же файл оказывается зарегистрирован и как Content plugin, и как Lister plugin.
- F3 (только в `combo`) на файле из поддерживаемого списка форматов (фото/видео/аудио) открывает предпросмотр без ошибок и без падения TC.
- Видео и аудио можно поставить на паузу, перемотать, отрегулировать громкость; fullscreen с overlay-контролами работает на нескольких мониторах.
- Переключение между файлами в папке (стрелки в Lister) работает без утечек памяти/COM-объектов (проверено при длительной сессии, например 100+ переключений).
- Крах декодирования одного файла (битый/неподдерживаемый файл) не приводит к падению TC — показывается заглушка/сообщение об ошибке. Актуально для обеих сборок.
- README обновлён и отражает актуальный функционал, включая объяснение разницы между `wdx`-only и `combo`.
